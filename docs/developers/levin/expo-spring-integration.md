# WiseEASE — интеграция Expo и Spring

Ветка `codex/levin-expo-spring-integration` основана на `main` с уже слитым Spring-бэкендом (PR #6). Фронтенд обновлён из `main` после PR #7 (`69d511c`). Цель — проверить существующий сценарий Марии и Никиты, сохранив экраны команды.

## Что подключено

- Существующий выбор роли открывает Spring-сессию демоаккаунта. Zustand применяет снимок после действий и запрашивает `GET /state` каждые 1,5 секунды при активном приложении.
- Мария видит баланс и историю и может отправить перевод знакомому получателю. Никита видит заявку в семейном разделе, может одобрить или отклонить её, изменить порог и проверку новых получателей. Статус и баланс Марии обновляются без ручного обновления.
- В `GET /state` добавлен `accountBalance` для собственного баланса вошедшего аккаунта. Для Никиты `balance` по-прежнему `null`: защищаемый остаток видит Мария.

## Что нужно для согласованного MVP

| Сценарий | Spring | Следующий шаг в Expo |
| --- | --- | --- |
| Вход | Демоаккаунты уже есть | Для прототипа используем текущий выбор роли. |
| Новый получатель | Есть поиск по Wise ID | Поле нового экрана ищет в Spring. Для нового получателя в демо можно ввести `@anna`. |
| Причины одобрения | Есть причины в предпросмотре и заявке | Никита видит причины на существующем экране. У Марии остаётся общий статус ожидания. |
| Список для денежных запросов Марии | Есть список разрешённых людей и его изменение Никитой | Никита меняет список в правилах, Мария видит изменения в своём списке. Демонстрационная ссылка остаётся на существующем экране. |
| Help и правила Марии | Есть порог и проверка новых получателей; изменять их может только Никита | Показывать Марии оба правила только для чтения и оставить звонок в Help. При отключении правило действует ещё 24 часа. |

## Синхронизация с PR #7

- В `request.tsx` оставлена новая карточка и кнопка Share. Список берётся из `requestPeople`; экран закрывает форму суммы, если выбранный контакт пропал. Ссылка демонстрационная и не создаёт запрос через API.
- В `rules.tsx` сохранены новые переключатели и отсчёт. Отключение и отмена читаются из Spring. Рядом с правилами помощник управляет списком для денежных запросов.
- `send.tsx` использует поиск по Wise ID и историю получателей из Spring. Снимок аккаунта передаёт имя и Wise ID в аватары и карточки текущей роли.
- В новом интерфейсе удалён маршрут `/send-maria`. Прямой перевод поддерживается API и локальным тестом Spring.
- В двух сессиях Expo Web на изолированной демосхеме прошли поиск по Wise ID и перевод Анне, одобрение и отказ, синхронизация списка и отмена отключения защиты. Действия в Full Wise вне семейного сценария, например карты и обычные платежи, остаются демонстрационными.

## За рамками текущего прототипа

- Приглашения, несколько подопечных на одного помощника и снятие защиты. Старый экран приглашения остаётся демонстрационным.
- Рабочие ссылки на денежные запросы. Сервер сохраняет сам денежный запрос.
- IBAN, Scam Pause, ручные избранные для переводов, карты и регулярные платежи.

## Задержка отключения и список денежных запросов

- Spring сохраняет срок отключения проверки порога и проверки новых получателей в миграции `V2__wiseease_protection_delay.sql`. Правило применяется до истечения 24 часов. Включение отменяет отключение или снова включает правило. Уже созданные заявки сохраняют свой статус и причины.
- В `frontend/app/rules.tsx` существующие переключатели показывают состояние из Spring. Список для денежных запросов использует `requestPeople`, отдельно от получателей переводов. В `frontend/app/request.tsx` этот список обновляется у Марии через `GET /state`.
- Слой Expo обновляется в `frontend/lib/wise-store.ts` и `frontend/lib/wise-spring-api.ts`. Методы описаны в едином [контракте Spring API](../nikita/wise-lite-api.md). Flyway обновил существующую демосхему. Проверили задержку, отмену, истечение срока и права через API. В двух сессиях Expo Web контакт появлялся и исчезал без перезагрузки, а переключатель показывал предупреждение и позволял отменить отключение.

## Предыдущий шаг: прямое подключение, перевод помощника и сброс

- Подключение: уже вошедший владелец указывает Wise ID существующего помощника. Связь появляется сразу, один помощник на одного владельца. Если кто-то уже связан, новая связь не создаётся. Регистрацию и приглашения не добавляем.
- Перевод: помощник отправляет деньги со своего баланса только своему подопечному. Списание и зачисление атомарны; повтор отправки с тем же ключом не списывает деньги повторно.
- Сброс: работает только в деморежиме для Марии или Никиты. Восстанавливает четыре демобаланса, исходную историю и правила. При наличии переводов между демо и другими аккаунтами сброс отклоняется.
- Изменения ограничены фичей `backend/.../wiselite/`, её API-контрактом и вызовами двух существующих действий в `frontend/lib/wise-store.ts`. Схема БД, конфигурация сборки и экраны остаются прежними. Новый экран подключения пока не нужен.
- Push-уведомления исключены из прототипа. Заявки на одобрение и их статусы обновляются в открытом приложении через существующий `GET /state`.
- Проверка: компиляция Spring, TypeScript и lint. На отдельной схеме PostgreSQL прошли HTTP-проверки всех трёх операций, включая повтор перевода, права и защиту сброса от затрагивания других аккаунтов. Полный набор тестов не запускаем. Коммит — только по отдельной просьбе.

- Серверный снимок: `backend/src/main/java/com/team/hackathon/features/wiselite/application/Households.java`. Единый [контракт API](../nikita/wise-lite-api.md), [инструкция запуска](../../../backend/README.md).
