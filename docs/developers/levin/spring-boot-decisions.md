# WiseEASE backend decisions

| Decision | How it works | Where to look |
| --- | --- | --- |
| Sign-in and permissions | Maria and Nikita sign in with email and password. The server stores the password hash and the hash of a random session token. Nikita receives the assigned account's history, rules, and approval requests. Maria's balance is `null` in his snapshot. | `application/Sessions.java`, `application/Households.java` |
| Migrations and demo data | Flyway creates the `we_*` tables in the dedicated `wiseease` schema. Hibernate validates the schema. A repeatable SQL migration loads demo data with a fixed password when `WISEEASE_DEMO_ENABLED=true`. The flag contributes to the checksum, so demo mode can be enabled after a regular start. The migration skips the insert when the demo household already exists. The prototype pairs one owner with one helper. | `backend/src/main/resources/db/migration/V1__wiseease_schema.sql`, `backend/src/main/resources/db/migration/R__wiseease_demo_seed.sql` |
| Data access | Spring Data JPA runs standard queries. Repositories use pessimistic locks when changing rules or settling transfers. After taking the locks, the server checks expiration against the database clock. | `infrastructure/entity/`, `infrastructure/repository/`, `application/Transfers.java` |
| Approval reasons | An amount strictly above the threshold produces `ABOVE_THRESHOLD`. If the new-recipient rule is enabled, a recipient with no successful transfers from Maria produces `NEW_RECIPIENT`. The server checks the reasons again at creation and stores them with the transfer. | `application/Transfers.java` |
| Transfers and balances | EUR amounts use `BigDecimal` and `numeric`. Funds remain available while a transfer is `pending`. A direct transfer or approval updates the status and both balances in one transaction. If funds are insufficient at approval, the transfer remains pending. | `application/Transfers.java` |
| Retries | If the outcome is unknown, the client retries with the same `Idempotency-Key`. The same sender, recipient, amount, and key return the existing transfer ID. Reusing the key with a different amount or recipient returns `409`. | `application/Transfers.java`, `backend/src/main/resources/db/migration/V1__wiseease_schema.sql` |
| Approval deadline | An approval request lasts 12 hours. At expiration, the server stops accepting decisions and shows `declined` with `expired: true`. The server checks the deadline after acquiring the lock. | `application/Transfers.java`, `application/Households.java` |
| Rule changes | Disabling threshold or new-recipient checks takes effect after 24 hours. PostgreSQL stores the deadline. The server uses it when reading state and creating transfers. Existing requests retain their reasons in the history. | `application/Households.java`, `application/Transfers.java` |
| Synchronization | `GET /state` reads the balance, history, and settings from one PostgreSQL snapshot. Expo can poll for that snapshot once integrated. | `application/Households.java` |
| Money requests | The server accepts requests only for people on Nikita's list. After saving a request, it returns the ID and state. The balance stays the same. | `application/Households.java` |

Main Java file paths are relative to `backend/src/main/java/com/team/hackathon/features/wiselite/`. See the [setup guide](../../../backend/README.md) and [shared API contract](../nikita/wise-lite-api.md) for working HTTP examples.
